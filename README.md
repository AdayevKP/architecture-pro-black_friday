## Как запустить

Перейти в директорию [sharding-repl-cache](./sharding-repl-cache)

```shell
cd sharding-repl-cache
```

Запускаем mongodb и приложение

```shell
docker compose up -d
```

Инициализация кластера mongodb c репликами

```shell
./scripts/mongo-init-replicas.sh
```

Если запуск скрипта выдает ошибку
`MongoNetworkError: connect ECONNREFUSED 127.0.0.1:27020`
то надо подождать 30 секунд и запустить снова

Заполнение данных в mongodb

```shell
./scripts/mongo-init.sh
```

Показать количество записей на шардах

```shell
./scripts/mongo-shards-data.sh
```

## Задание 7

Выбираю шард ключи и статегии шардирования для коллекций в MongoDB

Схема для [заказов](schemas/mongo/orders_schema.json)

Запрос на который больше всего может влиять шардирование

- Поиск истории заказов конкретного пользователя

Тут есть смысл отправлять заказы одного пользователя на один шард, значит буду шардировать по user_id
тут есть 2 варианта:

- range_based - пользователи прибавляются постепенно, часть шардов будет долго пустовать. к тому же старые пользователи окажутся на одном шарде и у них будет больше всего заказов и они забьют шард
  поэтому лучше взять
- hash based чтобы перемешивать новых и старых пользователей.
  может оказаться так что у пользователя будет очень много заказов
  и они забьют шард, но тут я предполагаю что количество пользователей сильно больше чем количество заказов которые может сделать один пользователь
  (скажем пользователей десятки тысяч, а заказов у одного максимум 1000), в таком случае такой проблемы нет.

Схема для [товаров](schemas/mongo/products_schema.json)

обратим внимание на 2 запроса

- Частые обновления остатков при покупках.
- Поиск товаров по категориям и фильтрация по диапазону цен.

Сделаю так чтобы товары в одном ценовом диапазоне и категории оказались по возмождности на одном шарде.
Проанализирую распределение товаров по ценам и по категориям и на основании этого сделаю range based шардирование
по двум ключам, категория и цена. Напрмиер будут шарды: Электроника 0-1000р, Электроника 1000-10000р и т.д или может быть один шард
Книги 0-5000р (например если книг мало продается)

Обновления выполняются точечно, поиском товара и его обновлением, тут будет преимущество если для обновления будут использоваться разные шарды, тогда нагрузка на обновление распараллелится.
Тут есть 2 варианта

- в корзине пользователя товары из разных категорий на разную сумму, тогда нагрузка распределится
- в корзине много одинаковых товаров - вся нагрузка пойдет (скорее всего) на один шард. Предполагаю что
  покупатели не будут заниматься оптовыми закупками и чаще будет встречаться первый вариант.

Схема для [корзин](schemas/mongo/carts_schema.json)

Тут нужно просто равномерно распределить корзины по шардам, с возможностью определять шарды по user_id или session_id, потому что именно по ним происходит поиск.
Среди запросов нет каких-то массовых выборок, кроме удаления старх корзин, но тут можно просто пройтись по всем шардам и удалить все что заэкпайрилось.
Для слияния корзин в целом нет разницы, на одном шарде или на 2х находятся корзины, потому как это всего 2 запроса, большой роли не играет.
Если на 2х шардах то можно распараллелить чтение, но опять же не думаю что существенно.
Из-за того что user_id и session_id могут быть null сделаю шард ключом вычисляемое значение shard_key = user_id or session_id и применю hash based шардирование

## Задание 8

Из-за категории «Электроника» произошла перегрузка одного из шардов MongoDB,
так как 70% запросов приходилось именно на эти товары.
Поэтому сейчас нужно разработать стратегию, как выявлять и устранять такие «горячие» шарды,
а ещё предложить метрики мониторинга, чтобы в будущем можно было предотвращать такие ситуации.

Метрики

- использование RAM и количество чтений с диска - поможет понять упираемся ли в объемы данных
- загруженность CPU - поможет понять не упирается ли шард в количество вычислений
- время выполнения запросов - измеряем нагруженность шарда в целом
- количество подключений к шарду - как много клиентов сразу читают/пишут данные
- размер каждого шарда, объем данных на нем - поможет понять не пора ли разбивать шард на несколько более мелких

Автоматическое перераспределение данных

- по данным в шарде строится распределение данных в диапазонах цен и категориях, текуший шард разбивается на несолько так,
  чтобы в каждом было примерно одинаковые объемы данных. Шардирование происходит как описано в предыдущем задании, а именно range based по категории и цене.
- по метрикам утилиззации RAM, CPU можно принять решение о выделении дополнительных ресурсов конкретному шарду

UPD: другой вариант перебалансоровки, основанный на zoned tag sharding
- в mongo создадим зоны шардов hot, cold
- для шардов в зоне hot выделяем значительно больше ресурсов
- добавляем метрику популярности товаров, например, количество покупок/просмотров в день/неделю
- по метрикам можно определить в каких диапазонах категорий и цен находятся самые популярные товары
- с зоной hot ассоциируем популярные диапазоны, соотвественно из зоны cold надо эти диапазоны убрать
- после ассоциации диапазонов балансер mongo переместит товары из нужных диапазонов на соответствующие шарды https://www.mongodb.com/docs/manual/core/zone-sharding/#balancer
- в будущем если популярные товары изменятся, то по метрикам можно определить новые популярные диапазоны и привязать их в hot shards. Процесс можно попробовать автоматизировать

### Целостность (консистентность) критична для:

- **Остатки товаров** — расхождение приводит к overselling, финансовым потерям.
- **Заказы** — заказ должен быть сохранён ровно один раз и не должен изменяться после подтверждения. При создани списать отстатки в транзакции. Потеря заказа или дублирование приведут к финансовым потерям.
- **Слияние корзин** — потеря не критична, но не желательна, т.к ухудшит пользовательский опыт.

### Скорость обработки критична для:

- **Активные корзины** — частые операции добавления/удаления товаров
- **Проверка остатков при оформлении заказа** — влияет на время подтверждения заказа и пользовательский опыт.
- **Поиск товаров в каталоге**

### Для каких данных Cassandra имеет смысл:

### Концепутальная модель Cassandra для корзин

#### Запросы к корзинам

- Получение корзины по `user_id` или по `session_id`.
- Частые операции добавления/удаления товаров.
- Поддержка TTL для автоматической очистки неактивных корзин.

#### Структура таблицы `carts`

```cql
CREATE TYPE IF NOT EXISTS item (
    product_id UUID,
    quantity INT,
    price DECIMAL,
    name TEXT
);

CREATE TABLE IF NOT EXISTS carts (
    cart_key TEXT,
    cart_id UUID,
    user_id UUID,
    session_id TEXT,
    items LIST<FROZEN<item>>,
    status TEXT,
    created_at TIMESTAMP,
    updated_at TIMESTAMP,
    expires_at TIMESTAMP,
    PRIMARY KEY (cart_key)
);
```

Первичный ключ: `cart_key = сoalesce(user_id, session_id)` (partition key) </br>
Partition key: hash от cart_key, обоснование такое же как для таблицы корзин в mongo, равномерно распределяем данные по шардам. </br>
Риск дисбаланса возможен, если один пользователь создаёт множество корзин, но это запрещено на уровне приложения.

#### Операции

- **Чтение корзины:** Один запрос `SELECT * FROM carts WHERE cart_key = ?` с указанием вычисленного ключа. Запрос попадает в один шард и выполняется быстро.
- **Запись корзины:** Одна операция `INSERT`/`UPDATE` по `cart_key`. Нет batch-записей, запрос идет на нужный шард и выполняется.
- **Удаление/обновление по TTL:** Cassandra поддерживает TTL на уровне строк, можно установить `expires_at` и использовать `USING TTL`.

#### Горячие партиции

- Если один пользователь производит аномально большое количество операций, его партиция может стать горячей. Однако это маловероятно в реальном сценарии, так как даже активный пользователь не генерирует тысячи запросов в секунду к одной корзине.
- Rate limiting добавлений в корзину на уровне приложения поможет избежать горячих партиций
- Мониторинг и блокировка аномальной активности по `cart_key`.

#### Решардинг

Cassandra использует consistent hashing, поэтому добавление или удаление узлов приводит к перемещению части данных (решардинг).

- `cart_key` распределён равномерно, решардинг затрагивает примерно `1/N` данных каждого узла, что является стандартным сценарием.
- Временное увеличение сетевого трафика и нагрузки на диски может незначительно повлиять на производительность операций с корзинами во время перебалансировки.</br>
  Как проводить решардинг:

1. Виртуальные узлы (vnodes) для более плавного перемещения данных.
2. Добавлять узлы по одному, давая кластеру время на перебалансировку.
3. Выполнять решардинг в периоды относительно низкой нагрузки (например, ночью).
4. Отслеживать метрики сети, дисков и задержек во время процесса.

#### Стратегии целостности данных

| Стратегия               | Настройка                      | Обоснование                                                                                                                                         |
| ----------------------- | ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Hinted Handoff**      | Включён                        | Позволяет продолжить запись при временной недоступности реплики и быстро восстановить утерянные записи                                              |
| **Read Repair**         | При чтении для создания заказа | При создании заказа важно согласовть данные, чтобы использовать актуальную корзину в заказе                                                         |
| **Anti-Entropy Repair** | Запуск раз в день              | Гарантирует долгосрочную согласованность, особенно для корзин с длительным TTL. Поскольку корзины часто обновляются, ежедневного repair достаточно. |

#### Уровень согласованности (Consistency Level)

- Запись: `LOCAL_QUORUM` – баланс между доступностью и гарантией записи на большинство реплик в дата‑центре.
- Чтение: `LOCAL_ONE` – минимальная latency, данные читаются с одной реплики.
